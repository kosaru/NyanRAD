# NyanRAD 初期範囲の比較案

作成日：2026-10-22／追跡：[Issue #2](https://github.com/kosaru/NyanRAD/issues/2)

本書は開発要求受付の判断材料。初回候補・後続候補の区分を検討の軸とすることについて、要求者から「はい、それで進めてください。」との了承を得た。詳細な提供範囲は要件定義で具体化する。判断の根拠は[判断履歴](decision-log.md)を参照。

## 目的と前提

NyanQLフレームワーク群をVB6のような統合開発環境で使えるようにする。ブラウザで部品を配置し、通常のNyanQL群の体裁を保った編集可能なソースコードを生成する。
特定の業務アプリに用途を限定しない。

人間から示された方向：
- NyanPUI・Nyan8・NyanQLを扱う。
- NyanPUI→NyanQLとNyanPUI→Nyan8→NyanQLの両構成を扱う。
- 実行ファイルは要求者側で用意する。
- まずNyanQL内蔵DBを利用する。SQLite・DuckDBの既定値・詳細対応範囲は未確定。

## 初回候補：開発の一巡を成立させる

| 操作 | 初回に含める候補 | 完成を判断する観点の案 |
|---|---|---|
| プロジェクト作成 | 新規作成、開く、保存、製品別ファイル一覧 | NyanPUI・Nyan8・NyanQLのファイルと設定を見つけて編集できる |
| フォーム作成 | 複数フォームの追加、切替、名前変更 | 保存して開き直しても画面構成が残る |
| 部品配置 | ラベル、入力欄、複数行入力、ボタン、チェック、選択欄、一覧表 | 配置、移動、サイズ変更、削除、コピー、整列ができる |
| プロパティ | 名前、表示文字、位置・寸法、表示、有効状態 | 設定が生成ソースと実行画面へ反映される |
| 操作のやり直し | 配置・プロパティ変更のUndo／Redo | 誤操作から復帰できる。保存後の履歴保持範囲は別途定義 |
| イベント編集 | 部品のダブルクリック、対象・イベント選択、コード編集 | イベントから処理が実行され、再配置しても手書き本文が残る |
| Nyan8編集 | サーバーJavaScript、API定義、関連設定の編集 | 画面からNyan8の処理を呼び出せる |
| NyanQL編集 | SQL、API定義、内蔵DB接続設定の編集 | 画面操作からデータの登録・参照・更新・削除を確認できる |
| 接続 | 直接接続とNyan8経由を選べる構成 | それぞれの経路でJSONデータを受け渡せる |
| 実行・停止 | 設定した実行先で起動・停止、プレビュー、ログ・エラー表示 | 変更を保存し、実行結果と失敗箇所を確認できる |
| ソースの保存・再編集 | HTML・CSS・JavaScript・SQL・JSONの保存、対応範囲の再読込 | 再配置しても手書き処理を保持し、競合時に上書きを止められる |
| 生成物の利用 | 通常ファイルとして取り出す | NyanRADを起動せず、対応するNyanQL群でアプリを実行できる |

表は詳細仕様・テスト契約ではない。一覧表の列編集・データ結合、イベント種類、複数画面間の値渡し等は要件定義で具体化する。
初回部品数を減らす案も比較可能だが、SQLとNyan8の編集を初回から含めることで、フレームワーク群を扱う目的を確認しやすい。

## 後続候補と、初回へ含めた場合の影響

| 後続へ回す候補 | 初回への影響 |
|---|---|
| VB言語互換、既存VB6プロジェクト取込、COM／ActiveX互換 | 言語処理系やWindows依存機能の再現まで範囲が広がる |
| ブラウザ・サーバーをまたぐブレークポイントデバッガ | サーバー実行基盤の調査とデバッグ支援が必要になる |
| 任意HTML／CSS／動的DOMの完全なデザイナー逆変換 | 対応できないソースを含む往復編集の保証が大幅に難しくなる |
| 独自部品の配布・拡張機構 | 部品API、互換性、配布の仕組みが必要になる |
| 複数人の同時編集、組織・権限管理 | 競合解消、利用者分離、共有運用まで必要になる |
| 本番への自動配備、クラウド運用 | 配備先、認証、復旧、運用条件の定義が必要になる |
| 外部DB向けの専用設定・検証支援 | 内蔵DB以外の実行環境と互換性検証が増える |

後続候補の機能も、通常のソースコードとして開発者が記述できる範囲と、IDEが専用操作で支援する範囲は区別する。

## 要件定義で解決する事項

| 論点 | 比較する方向 |
|---|---|
| 利用・実行先 | ローカルで一人が使う構成／共有サーバー構成。保存場所・起動管理・権限への影響を比較 |
| コード言語 | 標準JavaScriptでイベントを書く案／VB風記法を追加する案 |
| 配置 | 固定座標中心／画面幅に追従する配置／両者の組合せ |
| 手編集と再編集 | IDEの対応範囲を明示し範囲外を保持する案。保証範囲と競合操作を定義 |
| DB | SQLite・DuckDBのどちらを既定にするか、初回に両方をどこまで検証するか |
| 提供条件 | 実行ファイルの版・対応OS・ブラウザ、ライセンス、期限、受入条件 |
| 受付上の不足 | 対象利用者、現在の困り事、改善の判断方法、初回対象外の人間判断を確認 |
| GitHub運用 | 初回開発中の正式要件の保存先・ブランチと正式版切替の対応を整理 |

## 人間に判断してもらう内容

「開発の一巡」と初回・後続の区分を検討の軸とする了承は記録済み。
さらに、対象利用者・困り事・期待する変化・初期対象外を整理し、受付規則のcandidate条件が揃ったところで要件定義への着手判断を求める。

範囲案への賛同を、未確定の詳細要件や実装開始の承認へ読み替えない。着手判断後は正本の「要件定義、その前に」から工程順に進める。
