# ローカル保存・実行管理の成立条件（調査資料）

## 確認された方針

要求者はローカル利用を基本とすること、リモートサービス利用はNyanQL群側で扱うことを示した。
続いて、既存機能で保存・起動・停止をどこまで実現できるか調査し、追加実行ファイルの必要性を判断する方針を了承した。
専用管理サービスの追加採用は未決定。追加の人間判断により、初回対象OSはmacOSとする。

## 既存ソースで確認した機能

| 製品 | 保存・読込 | コマンド実行 | 調査から分かる限界 |
|---|---|---|---|
| NyanPUI | nyanGetFile、nyanSaveFile(path, content)、nyanDeleteFile(path) | nyanHostExec | 保存は一時ファイルへ書き同期・閉じた後にRename。コマンドは出力収集と終了を待つ |
| NyanQL | nyanGetFile、nyanSaveFile(base64, path) | nyanHostExec | PUIと保存関数の引数形式が異なる。コマンドは終了を待つ |
| Nyan8 | nyanGetFile、nyanReadFileB64 | nyanHostExec | 今回確認した通常API用の登録には保存関数が見つからない。コマンドは終了を待つ |

Nyan8だけを見た前回の保存比較を補足する。NyanQL群全体には保存機能があり、保存だけを理由に追加実行ファイルが必須とは言えない。
PUIの単一ファイル保存手順があっても、複数ファイルの一括保存・外部編集との競合防止が完成しているわけではない。OS別の上書き動作も採用バイナリで検証する。

## 追加実行ファイルを前提にしない構成候補

ローカルのNyanPUIでNyanRAD画面と管理APIを配信し、サーバーJavaScriptから既存の読込・保存・削除機能を使う。
NyanRAD本体のファイルと生成アプリのプロジェクトを区別する。
生成アプリのNyanPUI・Nyan8・NyanQLへ、各製品の通常設定とソースを渡して実行する。

起動・停止は、短時間で終わるOS側の操作をnyanHostExecから呼ぶ案を検討する。サーバー本体をそのまま同期呼出しすると終了まで返らないため、常駐プロセスの切離しと出力先の扱いが必要。
WindowsとmacOS／Linuxでは起動方法や停止方法が異なる。OS標準の仕組み・配布スクリプトで成立するかは未実証であり、「追加バイナリなし」をまだ保証しない。

## 成立を確認する項目

| 項目 | 必要な確認 | 現在の評価 |
|---|---|---|
| 読込・保存・削除 | 日本語・改行・空白を含むパス、親ディレクトリ、保存失敗、対象範囲 | 既存関数あり。アプリ側の制御・試験が必要 |
| ファイル一覧・名称変更 | 索引と実ファイルの整合、外部変更の扱い | 専用管理APIを組む必要がある |
| 競合・複数ファイル保存 | 読込時版との比較、途中失敗、実行への反映単位 | 既存保存関数だけでは未充足 |
| 起動 | 設定ファイル・作業場所・ポート・起動失敗を対応づける | コマンド機能あり。常駐起動の実証が必要 |
| プロセス追跡 | IDEが起動したものを識別し、PID再利用やIDE再起動後を扱う | 管理処理の追加と検証が必要 |
| 停止 | 他のプロセスを止めず、終了待ち・異常終了を扱う | OS別方式を検証する必要がある |
| ログ取得 | ファイル等への出力、取得位置、ローテーション、文字コード | 各製品のログと取得用APIを組み合わせて検証 |
| 再実行 | 保存内容、設定変更、再起動要否を揃える | ホットリロードだけで全変更反映とは扱わない |

コマンド機能へ編集本文や入力パスをそのまま連結しない設計が必要。保存先の制約・実行対象の対応・起動したプロセスの所有関係を管理API側で定義する。

## 現時点の結論

保存はNyanPUIの既存機能を使う構成が有力。起動・停止はOS側処理と組み合わせる候補があるが、所有管理を含めた成立確認が残る。
したがって、現段階で専用管理サービスの追加が必須とも不要とも確定しない。
初回対象OSのmacOSについて、正式な要件・作業指示の下で保存・起動・停止・ログの実証を行い、成立しない条件を具体的に示して代替案を比較する。フレームワーク本体の変更は今回行わない。
