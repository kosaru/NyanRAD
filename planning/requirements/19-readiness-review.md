## 今回直した記述

DBの既定値・初回範囲、macOSローカル利用、固定座標中心、コピー時の本文保持、Undoとコード履歴の区別、保存後の履歴保持について、合意済みなのに本文に残っていた「未決定」を修正。
企画、全体像、要求一覧、UI、機能、データ、編集細目、提供条件、受入条件の計10文書を更新した。
判断履歴の過去の状態は履歴として維持し、未確認の詳細を新しく承認済みにしていない。

## 現在の確認済み事項

- NyanQL群をVB6のように利用するブラウザIDE。通常ソースを生成物とする。
- HTML・CSS・JavaScriptで構築し、提供されるNyanQL群実行ファイルを使う。
- 初回はmacOSローカル。追加専用バイナリは未採用。
- 固定座標中心、基本部品・イベント、通常JavaScript、一覧表の表示・行選択、対応範囲を明示した再編集。
- 未保存時の選択、競合差分、手書き保持、失敗表示、コピー・名前変更・Undoの確認済み方針。
- 部分保存時の新規起動禁止、二重起動回避、今回起動した対象だけの回復停止、タブ終了と停止の区別、不明状態の自動強制終了禁止。
- SQLite既定。SQLite・DuckDBの基本CRUDを直接とNyan8経由の両方で確認する。

## 承認準備の不足と次の作業

| 不足 | 次にAIが行う作業 | 人間判断との境界 |
|---|---|---|
| 概要と追記が多く、現在の仕様を通読しにくい | 確認済み事項と残る論点を統合した人間向け確認資料を作る | 既存合意を整理するだけなら再承認を求めない |
| 部品別項目、イベント引数・時機、一覧行キー、配置値等の細則 | 影響がある未決定と、実装担当が決める技術事項を分ける | 利用者の動作・提供範囲を変える細則は人間判断 |
| 実行管理の技術成立が未確認 | 既存能力の不足を特定し、要件と設計・実証の境界を整理 | 成立しない条件や新しい残存リスクを人間に戻す |
| 対応環境・実行ファイル版・提供条件 | 正式入力を固定する時点で必要な条件を列挙する | 事前にCPU等の詳細で企画の検討を止めない |
| Workset境界・IFDAM・Interactionが候補のまま | UI・機能・データに基づく正式候補を作る | 内容を確定する際は人間向け資料と一致させる |
| 図の固定版・構造化IFDAM・対応表・Schema検証がない | 人間向け図をSVG等で整え、同じ意味の構造化成果物と相互参照を準備する | 生成や形式検証はAI担当 |
| 単一リポジトリ初回運用のブランチ対応が未整理 | 初回の明示指示と正本を踏まえ、要件候補と実装の保存先を具体化する | 正式要件の保存先が不明なまま成立記録を作らない |
| 受入条件案全体の判断が未記録 | 合意を反映した版と証拠条件をそろえる | DB範囲の了承を受入条件全体の承認にしない |

現状の構造化IFDAM・Mapping・Snapshotがない状態で、Candidateを完成済みまたは引渡し可能とはしない。
技術実証を実装前の要件確定に必要とするか、設計・実装の検証条件として管理できるかは正本に照らして整理する。調査不足を無条件に残存リスクとして受け入れない。

## 次に進める順序

1. 確認済み要件の統合資料を作り、資料本文の残る古い未決定表現を解消する。
2. 利用者へ影響する残件と技術設計事項を分離して、人間が判断する項目を絞る。
3. Workset・IFDAM・構造化成果物・Mapping・固定Snapshotを準備し、形式と意味の一致を検証する。
4. Blockingな不足を解消した候補Commitを固定して正式判断へ提出する。

この報告の作成・修正は資料整備として実施。プロダクトの実装・配布・Releaseは行っていない。
